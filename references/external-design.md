# 外部设计 Skill 调用

外部 Skill 提供设计与实现方法，项目只使用一份经用户确认的 [Design Spec](../templates/design-spec.template.md)。用户指定的审美、实际内容、已有组件和任务范围优先。

## 选择与调用

| 任务 | 主 Skill 或按需专项 |
|---|---|
| 从零设计官网、落地页、作品集 | 优先调用 [Impeccable](https://github.com/pbakaus/impeccable)，选与品牌、新作或方案对应的指引；可用时也可选 [Anthropic frontend-design](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md)。用品牌内容、图像或实际产品证据定首屏。二者选一个为主。 |
| SaaS、后台、工具、编辑器、Dashboard、H5 | 优先调用 Impeccable 的产品界面、新作或打磨指引。已有高保真稿需要忠实复现时，可选 [Frontend App Builder](https://github.com/openai/plugins/blob/main/plugins/build-web-apps/skills/frontend-app-builder/SKILL.md) 做区域校准。原生移动端以目标平台与项目系统为准。 |
| 已有界面显得粗糙或风格混杂 | 调用 Impeccable 的 `critique` 或 `polish`，先读项目主题和组件。区分布局问题、共享 token、组件变体和局部调用，再改到对应层。 |
| 悬停、按压、浮层或多状态切换需要专项处理 | 按需加 [Emil Kowalski 的设计工程 Skill](https://github.com/emilkowalski/skills/blob/main/skills/emil-design-eng/SKILL.md)。沿用同一套材质与反馈语言，按操作频次定表达强度；复查中断、回退和减少动效。 |
| 明确请求技术审核或有复杂响应、无障碍问题 | 可用 [Vercel Web Interface Guidelines](https://github.com/vercel-labs/web-interface-guidelines/blob/main/command.md) 定位技术问题；视觉判断由主 Skill 和已确认规格负责。 |

1. 优先调用当前环境已安装且适用的 Skill，读取实际版本的入口与相关动作。方案阶段只采用调研、创意与评审步骤，用户确认后才执行写代码、搭建项目或变更依赖的步骤。按当前项目权限选择工具与脚本。
2. 本地 Skill 未安装、工具不可用或前置流程不适用时，读取对应官方原文与必要章节。规格记录「直接调用」或「采用官方指引」，附版本或链接。
3. 本地与官方原文都不可用时，如实记「外部方法未访问」，用已确认的参考、已有组件和相关场景手册继续可完成的部分。用户点名要求该 Skill，或缺失的参考影响设计方向时，说明限制，请用户提供可访问版本或确认替代。

## 打开或查找外部参考

- 用户给了链接时，先尝试打开。需要补足构图、材质、组件或交互参考时，直接用当前环境可用的浏览器或搜索工具查同类真实页面、设计系统示例、公开设计稿或官方源码。预设、框架和交付物是否应离线运行，与能否在线找参考分别判断。
- 打开实际页面或截图再判断视觉，读相关代码或文档确认组件行为。若指定来源受权限、网络或工具所限，尝试同源的公开文档、官方示例或可访问的源文件。区分「看到实际画面」「只读到文档或源码」和「无法访问」。指定画面无法查看且会影响方案时，请用户给截图或确认替代。

## 把外部方法收敛到一套规格

1. 从可核对的项目参考中提取具体决策，例如「大图在桌面保持主体并置，手机以人物焦点裁切」「同组筛选共用高度和边线，选中以浅底和文字变化显现」。外部 Skill 是方法来源，实际参考或草案是视觉依据。用单一主方向组织整页。
2. 方案阶段用真实标题、内容、素材和数据描述代表区域，按需展示草图。先确定对齐线、阅读顺序和主视觉权重，再决定材质。每种表面有清楚的角色，同层组件共享边线、圆角和阴影规则。只在服务层级、品牌或交互时使用发光、玻璃、渐变和装饰。
3. 交付 Design Spec 并等用户确认。获确认后先把代表区域实现到项目中，宽窄屏并排检查，再把字阶、形状、颜色、组件状态和动效推广到全页。专项 Skill 在同一主题内改善局部反馈。
4. 在真实页面里检查首个阅读落点、边缘与裁切、组件一致性、鼠标与键盘反馈。发现问题时记录具体位置、触发方式、参考差异、修在何处，修后复看。
